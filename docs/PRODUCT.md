# 产品需求草案 v0.1

日期：2026-09-09。以下是根据讨论整理的起点，未验证的产品选择均可调整。

## 用户需求

每个人拥有自己的专属 Agent。当人与人之间产生需求时，让 Agent 先完成必要沟通，再把需要人判断的结论和问题交给主人。

我们希望减少反复询问、重复解释和信息搬运。支持工作与生活：会议预约、朋友聚餐、家庭出行、任务协调、商务需求澄清、科研设备预约。第一版仅验证两人约时间，其他场景保留为后续方向。

## 核心角色

| 角色 | 责任 |
| --- | --- |
| 主人 | 设置偏好和授权，确认或拒绝方案，撤销授权 |
| 专属 Agent | 理解主人的需求，在权限范围内提议、回答和协商 |
| Bridge | 校验身份与权限，传递消息，维护协商状态与必要记录 |
| 外部工具 | 在单独授权后查询日历或执行具体操作 |

认证一个 Agent 的技术身份不等于证明它有权替主人作出任何承诺。主人绑定、授权范围和有效期需要独立表达。

## 首个 MVP

MVP（Minimum Viable Product，最小可行产品）建议从已建立联系的两名用户开始，使用模拟日历和两个隔离的 Agent 适配器。

1. A 指定目标联系人、时间范围、时长和允许分享的内容。
2. A 的 Agent 向 B 的 Agent 发起请求。
3. B 的 Agent 依据 B 的授权，仅返回可分享的候选时段，也可以拒绝。
4. 双方在有限轮次内协商出一个具体方案。
5. 双方主人分别确认同一版本的方案；修改方案会使旧确认失效。
6. 生成双方可查看的确认结果。第一阶段仅模拟执行；真实日历写入在后续阶段接入。

明确区分“收到请求”“愿意协商”“确认方案”和“外部操作成功”。一方同意不代表另一方同意；日程写入失败不能显示为完成。

## 授权体验

用户可以允许自动交换指定范围的空闲时间，无须为每一条中间消息确认。正式预约在第一版要求双方确认。后续可研究用户预先授权的自动预约策略。

授权至少包含对象、信息类型、允许动作、适用任务和有效期；支持随时撤销。对方发来的文本不能修改本地主人的授权规则。

日志只保留必要的任务状态、确认版本和事件信息；保留时长与删除机制要在真实数据接入前确定。私人知识库和完整日历保留在各自一侧。

## 首版验收标准

- 两个不同用户的 Agent 能完成一次带往返消息的协商。
- 仅分享允许的候选时段，不能返回私人日程标题、联系人或知识库原文。
- 只有双方确认同一方案版本后才允许进入执行。
- 支持拒绝、撤销、超时和无共同时间；用户能看懂当前原因。
- 重复投递不能导致重复确认或重复执行；执行前再次检查授权和方案时效。
- 对方离线时显示等待，并在到期后停止重试；限制轮次、运行时间和模型预算。
- 真实日历阶段需执行前复查空闲情况，并处理一方写入成功、另一方失败的恢复流程。

## 后续需要验证的选择

- 第一批使用者日常使用哪些 Agent，它们提供何种正式接入方式？
- 约时间是否足够高频，还是需求澄清更能减少沟通？
- 主人希望逐次确认哪些事项，愿意预授权哪些动作？
- 先做网页入口是否足够，是否需要钉钉或手机通知？

具体 Agent、日历或消息平台的可接入性需要逐项核查，不能假设所有桌面 AI 产品天然支持外部收发消息。
