# 产品需求草案 v0.2

日期：2026-09-09。当前为产品探索阶段。下文区分用户已选择的方向与候选建议；尚无实现。

## 已选择：自动组织＋场景名片

用户已选择第三种产品方案：个人 Agent 根据本次需求，自动组织相关身份、信息与偏好，形成主人可查看、可调整的“场景名片”。场景名片是暂定产品名称，不是把主人的全部信息直接发给对方的公开资料卡。

- 同一个主人可以在不同场景下作为租客、游客、酒店房客或工作伙伴；身份之间可以共享相关偏好，不必维护多份互相隔离的个人档案。
- 场景名片表达本次身份、核心诉求、协商偏好、准备对外表达的信息，以及仅供本人 Agent 判断的内部参考。
- Agent 需要带着可执行的方案沟通，并根据对方反馈调整，不能只转达要求。了解个人偏好用于初步判断，不自动等于获得签约、付款或其他承诺权限。
- 首次遇到某类事情时展示组织结果，后续逐渐复用；具体展示时机、确认规则、复用范围与重大变化的界定仍待讨论。
- “加 Agent 好友”建立持续联系，同一关系下可以处理多件事情；联系关系本身不代表可以访问主人的全部信息。

这次选择确定的是产品方向。个人信息由 AB 保存还是由现有 Agent 提供、首个验证场景、界面形态和技术路线均未确定。

## 具体体验建议（待讨论，未选定）

建议流程：主人用一句话交代事情 → Agent 自动准备场景名片 → 双方 Agent 围绕方案沟通 → 谈妥的约定用于后续跟进。协商结果和实际签约、付款、执行结果需分别呈现。

建议采用“对话为主，名片随时可展开”的界面。主人视图包含本次目标、偏好、方案依据、内部参考和沟通进展；对方视图仅包含适合且获准对外表达的本次身份、诉求、方案与已达成约定。

首次或重要变化时主动展示名片，熟悉的日常事务尽量减少打扰。展示不等于要求每次确认，也不等于自动授予承诺权限；触发条件和授权范围需继续设计。上述流程与视图划分属于助手提出的具体建议，不能因用户要求同步文档就视为已经选定。

## 当前深入讨论的场景：租房

租房用于梳理真实需求，尚未选为首个最小可行产品。候选流程覆盖合同理解、押金协商、付款日期与过渡租期安排，以及续约跟进。

Agent 应说明条款和疑点；实际法律判断需依据适用地区、合同和有效来源，区分法律依据、条款清晰程度与个人利益取舍。当前未开展具体合同审核。

协商方案需要讲清双方顾虑，并补齐日期边界、计算依据和后续安排。结果应保留已达成约定、未解决事项和待主人决定的部分。签约、转账与自动接受附加条件的权限尚未确定。

## 用户需求

每个人拥有自己的专属 Agent。当人与人之间产生需求时，让 Agent 先完成必要沟通，再把需要人判断的结论和问题交给主人。

我们希望减少反复询问、重复解释和信息搬运。支持工作与生活：租房、旅行住宿、会议预约、朋友聚餐、家庭出行、任务协调、商务需求澄清、科研设备预约。首个验证场景尚未确定，约时间仅为早期候选。

## 核心角色

| 角色 | 责任 |
| --- | --- |
| 主人 | 设置偏好和授权，确认或拒绝方案，撤销授权 |
| 专属 Agent | 理解主人的需求，在权限范围内提议、回答和协商 |
| Bridge | 支持按身份和场景组织沟通信息，连接联系人，校验权限，维护协商状态与必要记录；与个人 Agent 的具体职责分配待定 |
| 外部工具 | 在单独授权后查询日历或执行具体操作 |

认证一个 Agent 的技术身份不等于证明它有权替主人作出任何承诺。主人绑定、授权范围和有效期需要独立表达。

## 早期候选：两人约时间（未选定）

MVP（Minimum Viable Product，最小可行产品）建议从已建立联系的两名用户开始，使用模拟日历和两个隔离的 Agent 适配器。

1. A 指定目标联系人、时间范围、时长和允许分享的内容。
2. A 的 Agent 向 B 的 Agent 发起请求。
3. B 的 Agent 依据 B 的授权，仅返回可分享的候选时段，也可以拒绝。
4. 双方在有限轮次内协商出一个具体方案。
5. 双方主人分别确认同一版本的方案；修改方案会使旧确认失效。
6. 生成双方可查看的确认结果。第一阶段仅模拟执行；真实日历写入在后续阶段接入。

明确区分“收到请求”“愿意协商”“确认方案”和“外部操作成功”。一方同意不代表另一方同意；日程写入失败不能显示为完成。

## 授权体验

在约时间候选方案中，建议允许自动交换指定范围的空闲时间，无须为每一条中间消息确认；正式预约建议先要求双方确认。逐次确认与预授权的具体边界尚未选定。

授权至少包含对象、信息类型、允许动作、适用任务和有效期；支持随时撤销。对方发来的文本不能修改本地主人的授权规则。

日志只保留必要的任务状态、确认版本和事件信息；保留时长与删除机制要在真实数据接入前确定。私人知识库和完整日历保留在各自一侧。

## 约时间候选方案的验收建议

- 两个不同用户的 Agent 能完成一次带往返消息的协商。
- 仅分享允许的候选时段，不能返回私人日程标题、联系人或知识库原文。
- 只有双方确认同一方案版本后才允许进入执行。
- 支持拒绝、撤销、超时和无共同时间；用户能看懂当前原因。
- 重复投递不能导致重复确认或重复执行；执行前再次检查授权和方案时效。
- 对方离线时显示等待，并在到期后停止重试；限制轮次、运行时间和模型预算。
- 真实日历阶段需执行前复查空闲情况，并处理一方写入成功、另一方失败的恢复流程。

## 后续需要验证的选择

- 第一批使用者日常使用哪些 Agent，它们提供何种正式接入方式？
- 约时间是否足够高频，还是需求澄清更能减少沟通？
- 主人希望逐次确认哪些事项，愿意预授权哪些动作？
- 先做网页入口是否足够，是否需要钉钉或手机通知？

具体 Agent、日历或消息平台的可接入性需要逐项核查，不能假设所有桌面 AI 产品天然支持外部收发消息。
