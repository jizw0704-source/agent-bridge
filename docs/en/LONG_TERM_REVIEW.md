# Persistent rooms and read-only translator PR review

[简体中文](../LONG_TERM_REVIEW.md) | [English](LONG_TERM_REVIEW.md)

2026-10-23. Persistent rooms and scoped PR review are locally implemented and verified. This PR’s compatibility and capacity changes are not deployed, and no real Wright review handoff has completed. The underlying persistent-contact release was separately deployed; see [v0.4.0 deployment](CONTACTS_DEPLOYMENT.md), which does not establish deployment of this PR. This change completes review argument compatibility, message capacity bounds, tests and operating instructions on top of existing persistent contacts/tasks.

Administrators explicitly select `--persistent`; `expires_at: null` means no automatic room expiry. Default rooms still expire after one day. Ten-minute single-use invitations, owner identity comparison over a known channel, mutual confirmation, authentication, pinned TLS, either owner's close, persistence and deduplication remain. Expired rooms are not resurrected. Persistent rooms allow 1000 requests per side and approximately 16 million stored characters before an explicit capacity error requires rotation. Certificate expiry remains independent and requires renewal.

Create with `node src/peer-cli.mjs create NEW-PEER SERVER-ADMIN HTTPS-ORIGIN CERTIFICATE-SHA256 --persistent --translator-review`. Windows explicitly joins using `node src/peer-cli.mjs join NEW-PEER INVITE-FILE --accept-translator-review`. Both owners compare identities, then execute `confirm PEER PEER-CODE-FROM-OWNER` and `run PEER`. Queue using `send-review PEER 1`, wait for the stable draft to be consumed, then `send-review PEER 2`. `close PEER` revokes both ends. Prefix each command with `node src/peer-cli.mjs`. Use the actual server administrator directory, not a different local relay credential; never publish credentials, invitations, or private identities.

The separate `translator-pr-review` task permits only PRs 1/2 of `LightningFlashEvE/esp32-english-translator`. The locally invoked preparer reads GitHub API metadata, fetches a commit-pinned base/head comparison, rechecks that the PR did not move, and hashes the diff. Relay and receiver validate strict fields, repository, PR number and integrity. This is not a GitHub authenticity signature. Each request is bounded to 512000 characters, each reply to 8000. Ordinary text or arbitrary commands are rejected. New PR commits require a new snapshot/review.

The model receives only diff data in an isolated read-only directory, starts a fresh review session, ignores user tool configuration, disables shell/execution/editing/browser/connector features, and rejects tool-action events. Code and comments are untrusted data. This review cannot inspect full repository context or claim build, tests, hardware acceptance, approval, merge or flashing.

Deployment remains pending legal server access: upload to a version directory, run checks/tests on the server, retain the previous current link and private state, stop the service cleanly, switch the link and restart. Do not blindly delete locks or overwrite credentials/messages. Verify advertised capabilities, update both receivers, create and mutually confirm a new room. First verify a bounded synthetic exchange, then queue real requests and report queued/received/replied separately. On failure restore the previous code link, never roll private message state back. Deployment requires authorized server access from an account owner; local checks do not establish remote readiness.

Checks: `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm test`, `git diff --check`. No separate formatter/linter/type-check/build exists. All automated checks and a real local Codex synthetic-diff review passed, with no tool-action events. Automated tests cover persistent restart/time advancement, invitation expiry, revocation, scope rejection, moving PRs and snapshot corruption, local authorization mismatch and no reply loop. These do not establish Windows/Wright/server/device acceptance.

Review follow-up: new requests reserve worst-case JSON-escaped reply space before admission. Failed/processing entries retain their state but do not repeatedly occupy inbox batches and starve later requests.
